# Host nginx config (reference copy)

`mindorajournal.com.conf` is a copy of the host-level nginx site config running
in production, taken from `/etc/nginx/sites-available/mindorajournal.com` on
2026-08-29.

**The server is authoritative, not this file.** Nothing reads this copy and
nothing deploys it. It exists because the host nginx config was, until now, the
only part of production with no version-controlled copy anywhere — it had been
hand-edited twice, and the only other copies were timestamped backups sitting on
the same machine it configures. If that VPS is lost, this is what you rebuild
from.

That also means it goes stale the moment someone edits the server. If you change
the live config, re-copy it here in the same commit:

```bash
ssh -i ~/.ssh/mindora_prod root@169.58.202.46 \
  'cat /etc/nginx/sites-available/mindorajournal.com' > docs/nginx/mindorajournal.com.conf
```

## What the config does

Three server blocks, in file order:

1. **`www` → apex, 301.** Both hostnames resolve to this VPS and used to be
   served identically by block 2, which search engines treat as duplicate
   content and split ranking signals across. The `$request_uri` in the redirect
   preserves the path — a redirect that dumps every URL on the homepage throws
   away the link equity it was meant to consolidate. The certificate covers both
   names (SANs: `mindorajournal.com`, `www.mindorajournal.com`), so this block
   terminates TLS for `www` before redirecting.

   `ipv6only` is deliberately not repeated here. It is set on block 2, which
   also binds `[::]:443`, and nginx rejects a conflicting repeat of that option
   for the same socket.

2. **The apex site.** Terminates TLS and reverse-proxies to `127.0.0.1:3001`,
   the `journal-frontend-prod` container. `/downloads/` is served straight off
   disk from `/opt/mindora-static/downloads/`, outside Docker entirely.

3. **Port 80 → HTTPS**, generated by Certbot. Its `$host` is preserved, so
   `http://www` takes two hops (`https://www`, then apex). Collapsing that to
   one would mean editing a `# managed by Certbot` block, which can be rewritten
   on renewal — and Google follows redirect chains of up to five, so the second
   hop costs nothing measurable.

Blocks carrying `# managed by Certbot` are Certbot's to rewrite. The `www`
redirect is a separate block on purpose, so a renewal cannot silently undo it.

## Applying a change safely

Never edit and reload blind — a bad config takes the whole site down, including
the API, since everything is proxied through here.

```bash
F=/etc/nginx/sites-available/mindorajournal.com
cp "$F" "$F.bak-$(date +%F-%H%M)"     # 1. back up
# 2. edit
nginx -t                              # 3. test BEFORE reloading
systemctl reload nginx                # 4. reload (not restart - drops no connections)
```

If `nginx -t` fails, restore the backup and test again before doing anything
else. Verify afterwards that the apex still returns 200 and does **not**
redirect, that `www` returns 301 with the path intact, and that
`/api/v1/auth/me` still returns 401 — a 502 there means the gateway proxy broke.
